# 0002 - 面板是全功能操作台，但操作走契约同路

日期: 2025-06（wayfinder 票 [#2](https://github.com/JoeWest9966/Farm/issues/2) 裁决）
状态: 已接受

## 背景

面板定位在规划初期被默认为 Symphony 式"只读监控 + 最小 HITL"。用户裁决推翻了这个默认：Farm 的前端面板是**全功能操作台**——几乎所有可操作的功能最终都要在面板上可达（分批交付）。这引出两个架构问题：操作走什么通道才不破坏票 1（ADR-0001）锁定的"契约零域知识 + 原子 claim 防双跑"拓扑；以及运行时可变配置（并发、tick）与"配置住被编排仓库"的原则如何共存。

## 决策

1. **面板 = 编排器契约的另一个客户端**。凡契约里有的操作（claim/release、agent 派发/abort/steer、merge 提议），面板与编排器走同一套 Farm 服务 API、同一原子 claim，没有私有后门。宿主自身的装卸与配置走一组独立的**宿主管理 API**（面板专用），与契约并存但边界分明。
2. **配置双层**：被编排仓库的 workflow 配置是基线；面板可施加**覆盖层**（Overlay）——运行时值、显式标记"这是临时覆盖"、重启后提示恢复，不写回仓库文件。
3. **信息架构**：主视图为票看板（票为中心，tracker 是总线；blocked/needs_attention 为一等列），下钻单票详情（attempts、turn、事件、token、workspace、transcript 只读流）。任务 DAG 图形化不进第一版。
4. **数据通路**：面板只消费宿主投影层（快照 API + 增量推送），不直连编排器或 pi 子进程（Presenter 模式，照抄 Symphony 的"前端不复制状态逻辑"）。
5. **HITL**：blocked/needs_attention 队列 + 只读 transcript 流 + 尾部 steer/follow_up 输入 + abort。面板不做写干预（改工作区走 git，改调度走覆盖层/配置）。
6. **通知**：关键事件外发通知通道做成宿主侧可插拔出口；面板常驻是第一版，通知载体另议。
7. **回放**：任务级时间线（票历史、attempts、可过滤事件日志），无逐事件 scrubber；transcript 不持久化全量（只留摘要）；Kron 深度审计不进 Farm 面板。
8. **批次**：①读 + steer/abort + claim/release + 刷新；②手动 dispatch、暂停/恢复 tick、覆盖层；③宿主管理面 + merge 审阅流（在票 1 的机械闸门之上加人工闸门）。
9. **token 记账**：绝对累计法（防重），按全局/每票/每天三维归集，单价表可配置。

## 考虑过的替代方案

- **只读驾驶舱 + 最小操作集（"面板能打断，不能指挥"）**——被用户直接否决：面板的愿景是全功能操作台。保留的部分是通道纪律：操作再多，也走契约同路，而非另开指挥专线。
- **面板私有管理 API 一把抓**——被否：会侵蚀契约的单一权威，面板变成绕过原子 claim 的旁路调度器。
- **配置写回仓库文件**——被否：临时实验（压并发）会污染仓库历史；纯内存覆盖又被否（重启行为漂移不可解释）。双层折中。
- **transcript 全量持久化**——被否：回放需求是任务级时间线，为死 agent 留全量对话的存储成本不值。
- **逐事件 scrubber 回放 / Kron 审计进面板**——被否：单用户驾驶舱的奢侈品；Kron 自己有自己的呈现。

## 后果

- 面板的功能清单以契约操作面为天然上限：契约没有的操作，先问"该进契约/宿主管理 API 吗"，而不是直接开私口。
- 票 6（持久化）收到明确账单：票历史、attempts 时间线、可过滤事件日志、覆盖层当前态、通知配置；无全量 transcript。
- merge 审阅流为第三批能力，其交互形态留在雾里（不阻塞本图其他票）。
- 通知载体选型（webhook/推送服务）成为新的待决问题。
